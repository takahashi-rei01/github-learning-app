基礎レッスン

実務でよく使う流れ

高橋さんのように、VSCodeで修正してGitHubに残す場合はこの流れが基本です。

1
作業前に最新化
git pull
GitHub側の最新状態を自分のPCに取り込みます。
2
ブランチを作る
git switch -c feature/header-fix
本番用のmainを直接触らず、修正専用の分岐を作ります。
3
VSCodeで修正
HTML / CSS / JSなどを編集します。AIに作らせる場合もこの段階です。
4
変更確認
git status
どのファイルが変わったか確認します。
5
コミット
git add .
git commit -m "ヘッダー表示を修正"
変更内容を履歴として保存します。
6
プッシュ
git push
GitHubに反映します。
7
Pull Request
変更内容を確認してからmainに取り込みます。CodexやClaudeにレビューさせると安全です。

おすすめ運用

普段は mainを直接編集しない のがおすすめです。
「機能追加」「デザイン修正」「不具合修正」ごとにブランチを作ると、元に戻しやすくなります。

よく使うコマンド

状態確認 
git status

今どのファイルが変更されているか確認します。

変更を保存対象にする 
git add .

すべての変更をコミット対象にします。

変更を記録する 
git commit -m "変更内容の説明"

変更内容を履歴として保存します。説明文は後から見ても分かる内容にします。

GitHubへ送る 
git push

ローカルPCのコミットをGitHubへアップロードします。

GitHubから取得する 
git pull

GitHub側の最新状態を自分のPCへ取り込みます。

ブランチ作成 
git switch -c feature/new-page

新しい作業用ブランチを作って、そのブランチに切り替えます。

ブランチ一覧 
git branch

現在あるブランチを確認します。

変更を一時退避 
git stash

途中の変更を一時的に避難させます。急に別作業が必要な時に便利です。

直前のコミットを確認 
git log --oneline

コミット履歴を短く確認します。

コマンド練習

「変更状況を確認するコマンド」を入力してください。

用語集

確認クイズ

困った時の見方

Gitで困った時は、まず git status を見るのが基本です。 何が未保存か、何をすればよいかのヒントが出ます。
ソース管理に何も表示されない

変更がすべてコミット済み、または保存されていない可能性があります。VSCodeでファイルを保存してから確認します。

pushできない

GitHub側が先に更新されている可能性があります。まず git pull で最新化してから再度pushします。

違うところまで変わった

AIや自動整形で広範囲が変更された可能性があります。コミット前に差分を確認し、不要な変更は戻します。

mainを直接触ってしまった

小さい修正なら問題ない場合もありますが、次回からはブランチ作業がおすすめです。大きな変更の場合は、ブランチを作り直して整理します。

何をコミットメッセージに書けばいい？

「何をしたか」が分かればOKです。例：健診ポータルのヘッダー文言を修正、Q&Aカードの表示崩れを修正

AIと組み合わせる時の注意

  • Codexに作らせる前に、目的を.mdに書く
  • Claude Codeには「変更差分のレビュー」を依頼する
  • 一度に大きく変えず、小さい単位でコミットする
  • 動いた状態をコミットしてから次の修正へ進む

GitHubは「壊さずに戻せるようにする道具」と考えると分かりやすいです。
